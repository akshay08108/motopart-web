# PartX Rider portal

The rider workspace is `/rider`, with a dedicated sign-in at `/login/rider`.
It shares the PartX Firebase project, but has its own navigation and views.
This is the browser pilot; no rider APK or background GPS service is included.

## First-time setup

1. Deploy Firestore rules: `firebase deploy --only firestore:rules --project partx-production`.
2. Deploy the secure API on Cloudflare Workers using `cloudflare/delivery-api/wrangler.jsonc`. Firebase stays on Spark; Cloud Functions is not required for the rider workflow. See the setup guide in `cloudflare/delivery-api/README.md`.
3. Operations creates rider accounts; public signup cannot grant the rider role.
   With Application Default Credentials on a trusted operations machine:
   `node functions/provision-rider.mjs --project=partx-production --email=rider@example.com --name="Rider name" --phone=+919876543210`
   The script requires dependencies installed in `functions/`. Never commit credentials.
4. Alternatively, create an Email/Password user in Firebase Authentication. Using its UID, create `users/{uid}` with `name`, `email`, `mobile`, `roles: ["rider"]`, and `activeRole: "rider"`. Create `riders/{uid}` with `name`, `phone`, `active: true`, `online: false`, and `activeDeliveryId: null`. These records must be created through trusted administration, not the public client.
5. The rider can use Forgot password on the rider login to set their password.
6. Save the store pickup address in Seller Settings. Customers must save the delivery or garage address before checkout. Map coordinates improve tracking; address-only locations still support external navigation.

## Workflow

- Rider signs in and goes online. Availability heartbeats run while the portal is visible. Sellers see riders with a heartbeat within two minutes and no active assignment.
- Seller packs a confirmed UPI-paid or COD order, opens its details, and assigns a rider. Self-pickup orders are excluded.
- Assignment reserves the rider transactionally. One rider cannot be assigned two active jobs, even if two sellers act simultaneously.
- Rider accepts, checks all items, and confirms pickup. Customer order status becomes On the way.
- Rider explicitly enables location sharing. GPS is throttled to at most one write every ten seconds and stops while the portal is hidden, offline, or the job ends. The customer map labels updates older than 45 seconds or low-accuracy fixes as delayed.
- Customer opens the order and requests a six-digit delivery code. It is generated by the server, valid for 30 minutes, and hidden from rider and seller clients. Five wrong entries lock verification for five minutes. The customer can request a fresh code after expiry or lockout.
- After handing over all items, the rider enters the code and records COD collection where applicable. The server atomically completes delivery, saves timestamps, releases the rider, and deletes location and OTP data. Retrying completion cannot change the saved delivery time.
- A seller can cancel before pickup. A rider can decline before acceptance. Both retain a closed assignment record and allow a new assignment.
- After pickup, a rider reports an issue and contacts the store. The job stays assigned. The seller can confirm a physical return to the store, releasing the rider and returning the order to Packed for reassignment.
- COD collection records who collected cash and when. It is **not** proof of settlement to the seller. COD reconciliation remains an operations responsibility.

## Data and security

- `deliveries/{deliveryId}`: server-managed immutable parties and item/address snapshots, lifecycle and COD collection timestamps.
- `riders/{uid}`: operations-managed dispatch profile. Riders can update only their own presence fields.
- `deliveries/{deliveryId}/location/current`: latest coordinate only. Assigned active riders may write after pickup. The associated customer, seller and rider can read.
- `deliverySecrets/{deliveryId}`: server-only OTP, expiry and attempt counter. No client reads or writes.
- `orders/{orderId}.riderDeliveryId`: set by the server. Clients cannot forge assignments or bypass the delivery code by editing the order's status.
- Existing orders without a rider keep the current seller fulfilment flow.
- The Cloudflare API reuses existing FCM device registrations for rider assignments, pickup/completion, issues and cancelled assignments. Foreground assignments also show an in-portal notice; sound requires the rider to enable alerts in the current browser session. Unrelated legacy Firebase trigger functions are separate from this API.

## Rider earnings

- `/rider/earnings` shows live completed-delivery earnings, awaiting payment, confirmed payments and separate COD cash totals. Filters use India time: today, the last seven calendar days, this month and all time.
- Operations can set `riders/{uid}.earningsPolicy` to `{ amountPaise: 5000, payer: "store" }` (example only; `payer` may also be `"partx"`). Only trusted administration can write this field. No rate is assumed by default.
- The delivery backend snapshots the policy when assigning a job. Its `earnings.status` starts as `PENDING_DELIVERY` and becomes `EARNED` only after successful customer-code verification. Cancelling or retrying a completion cannot accrue duplicate earnings. Changing a rider's rate cannot change an existing assignment.
- Old deliveries without a rate remain explicitly unrecorded until operations reconcile them. Do not calculate past earnings using today's rate.
- Payment is not automatic. After actually paying and verifying it, trusted operations may record `earnings.status: "PAID"` with a Firestore `earnings.paidAt` timestamp on that delivery. Client apps cannot mark earnings paid. There is no automated payout or COD settlement system yet; COD collection never counts as commission.

## Tests

Start the Firestore emulator on port 8082, then run:

```
FIRESTORE_EMULATOR_HOST=127.0.0.1:8082 node --test tests/firestore.rules.test.mjs
FIRESTORE_EMULATOR_HOST=127.0.0.1:8082 node --test functions/rider-service.test.js
FIRESTORE_EMULATOR_HOST=127.0.0.1:8082 node --test cloudflare/delivery-api/worker.test.mjs
node --experimental-strip-types --test tests/rider-earnings.test.mjs
```

All suites use demo projects and must not run against production data. Cloudflare tests verify signed-token authentication and real REST transactions against the local emulator, with mocked Google OAuth and FCM providers. The delivery lifecycle is shared by both backend adapters in `functions/rider-core.js`.

## Native app follow-up

The web portal cannot guarantee GPS updates with the screen locked. A dedicated rider app will need a location foreground service, permission handling, persistent tracking notification, offline retry strategy and device testing. Routing/ETA and automatic rider assignment are separate future features; the portal does not invent routes or arrival times.
